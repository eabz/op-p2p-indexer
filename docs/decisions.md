# Decisions

The dated history of the design: each decision as it was taken, with its reason and the
measurements behind it. Rows are never rewritten; a later row supersedes an earlier one
(Redis and ClickHouse are gone since 2026-10-04). The current system is in
[architecture.md](architecture.md), what is left in [roadmap.md](roadmap.md).

| Date | Decision | Why |
|---|---|---|
| 2026-10-03 | **No dependency on external services.** The indexer does not call an L1 or L2 RPC and does not embed op-reth. | Embedding a node needs a full state sync and an L1 endpoint, which defeats a lightweight indexer. An RPC is an external dependency. |
| 2026-10-03 | **Receipts and logs come from L2 execution peers, verified against the header.** The indexer asks execution nodes for a block's receipts over the execution p2p network (devp2p `GetReceipts`), recomputes the receipts root, and accepts them only if it equals the `receiptsRoot` in the sequencer-signed header. | Receipts and logs are not in gossip and not on L1. Fetching and verifying them needs no state and no execution, and peers are the same kind of dependency as gossip. A peer cannot forge them. |
| 2026-10-03 | **Be a good peer.** On gossip the node already validates and forwards blocks. On the execution network it will serve headers, bodies and receipts for the range it holds, with limits. It cannot serve state. | Peers tend to deprioritise or drop nodes that only download. |
| 2026-10-03 | **A local block archive for serving, on fjall**. Committed blocks are also appended, in their consensus encoding, to an embedded store. Serving reads Redis for unsafe blocks and the archive for committed ones; ClickHouse is never used to serve peers. It is part of the `storage` crate, behind the `ArchiveStore` trait. It keeps the whole history (the retention window it first had was removed, see the 2026-10-04 row on retention). | Serving history from ClickHouse would cost several queries per block, with the load driven by strangers. The whole history was estimated at 300 to 500 GB; measured on 2026-10-04, the full OP Mainnet archive (blocks 0 to 157,745,023, with senders) is about 914 GB in 28,184 files, larger because values are compressed one by one for fast reads. It grows by roughly 200 GB a year (a full OP Mainnet node is about 700 GB including state; our own measurement gives about 280 GB a year of headers and bodies at current block sizes). redb was built and measured first: it used 1.7 times the data on disk, returned no space when trimming without a slow full compaction, and its appends slowed as the file grew, so it is ruled out for that size. fjall is the only maintained, published, pure-Rust engine of the log-structured kind that suits append-and-trim data. NippyJar was evaluated and rejected: unpublished internal reth crate, receipts only in block order, two cargo-deny exceptions. |
| 2026-10-03 | **Trust model without execution.** Transactions are confirmed by L1 once their batch is derived. Receipts and logs are as trustworthy as the sequencer's signature over the header that commits to them. Independent proof would need execution, or output roots resolved on L1 after the challenge period. | Stated so users of the data know what each status means. The indexer will not serve balances, `eth_call` or traces: it has no state. |
| 2026-10-03 | *Fallback, not the plan:* receipts from our own execution, keeping an L2 state and replaying blocks. Only if execution peers stop serving us. | It works without any peer serving receipts, but needs the full state, an OP-correct EVM and upkeep for every hardfork. |
| 2026-10-03 | *Fallback only:* two states, a committed state (as of the last L1-committed block) and a live overlay of per-block changes for unsafe blocks. | Part of the execution fallback above; not needed if receipts come from peers. |
| 2026-10-03 | **L1 awareness comes from an L1 p2p layer**, not an L1 RPC. It supplies the safe and finalized heads. See the 2026-10-04 row on dispute games for how. | Same reason as the first row. |
| 2026-10-03 | **Storage is built first and is independent of all of the above.** It takes an already decoded block, with or without its receipts, as input (`DecodedBlock`). How the block is decoded and where its receipts come from is solved in later crates. | Nothing in storage depends on where the data comes from, so it does not have to wait. |
| 2026-10-03 | Redis holds unsafe (live) blocks and handles reorgs; ClickHouse holds L1-committed and backfilled blocks. | Live data is small and changes shape; committed data is large and append-mostly. |
| 2026-10-03 | The two stores are named **unsafe** and **committed**, not hot and cold (`UnsafeStore`, `CommittedStore`). | The split is whether L1 has committed a block, not how often it is read. |
| 2026-10-03 | **Users read through one query layer**, not from Redis or ClickHouse directly. It routes each request to the unsafe or the committed store and labels results unsafe, safe or finalized. | One API regardless of where a block currently lives; the Redis key layout and the ClickHouse schema stay internal and free to change. |
| 2026-10-03 | **Stored data is disposable until the first release.** Migrations may be edited in place and databases dropped and recreated. From the first release on, applied migrations are never edited and data is kept. | Nothing is deployed yet; getting the schema right is worth more than preserving empty tables. The first release is the threshold; it has not been defined yet. |
| 2026-10-03 | **One embedded engine: fjall.** The p2p node store (identity and known peers) moves from redb to fjall too, and redb leaves the workspace. Existing data directories are not migrated: a node gets a new identity and an empty peer list. | One storage dependency to understand and audit instead of two. Data is disposable until the first release. |
| 2026-10-03 | Redis, not DragonflyDB. | One block every 2 seconds needs no extra throughput, and fork choice relies on Lua scripts that build key names from a prefix, which Dragonfly may not allow by default (not tested). The standard protocol keeps a later switch cheap. |
| 2026-10-03 | One chain: OP Mainnet (a second was added on 2026-10-04, see the Unichain row). No dual-stack listening. No backfill of missed gossip blocks over op-node's consensus-layer request-response protocol (op-node is retiring it); backfill is planned over the execution p2p network instead (crate 4). | Decided during the p2p PR. |
| 2026-10-03 | **Promote now, backfill later.** Blocks are promoted to the committed store without waiting for receipts, and a hole in the committed range (a block missed on gossip) does not stall promotion: it is counted, the archive restarts, and backfill fills it later. `p2p` hands the pipeline the decoded block, not raw SSZ. | Nothing has receipts or backfill until the `el` crate exists; waiting would mean nothing is ever committed or pruned. Decoding once keeps SSZ out of the pipeline. |
| 2026-10-04 | **The `el` crate is built before peer access is proven**, on reth's network crates pinned to a release tag (a git dependency and one `cargo deny` sources exception). Receipts for new blocks first, backfill after. | The one-hour test showed fetching and verifying receipts works, but only 1 of 28 peers gave a session. The crate was built while a longer run measured access (stopped after one hour, see [el-viability.md](el-viability.md)). No usable published crate exists for the encrypted transport. |
| 2026-10-04 | **History is imported once, by a separate binary, and then served to peers.** No execution peer we reached serves blocks below the Bedrock block (105,235,063), and op-reth no longer imports them. `op-indexer-import` downloads the whole chain, from block 0 to the L2 block of the newest dispute game on L1, from an external archive (Envio HyperSync). It rebuilds every header, transaction and receipt, checks each block hash and the transactions and receipts roots, links the range by parent hash, and checks the top block against the dispute game's output root. It then writes the block archive. The running indexer never links or calls it. "No external services" therefore means none at runtime; one-time imports are allowed when everything is verified. | The legacy chain cannot be re-executed by a modern EVM, so the data has to be fetched, and importing the rest in the same pass is faster than syncing it from peers. Keeping the importer out of the indexer keeps its dependencies and its trust in an external service out of the long-running process. Serving the range afterwards lets other instances get it from peers. See [import.md](import.md). |
| 2026-10-04 | **The safe and finalized heads come from dispute games, not from deriving batches.** A beacon light client follows Ethereum from one trusted checkpoint and vouches for L1 execution block hashes. From those, the `l1` crate fetches L1 headers, bodies and receipts over devp2p, verifies them, and decodes the dispute games created for the chain. A game names an L2 block and its output root; when our block at that height gives the same root, it is safe, and finalized once the game's L1 block is finalized. There is no provisional head. | Deriving batches needs blobs, which L1 peers prune after about 18 days, and a full derivation pipeline. A game's output root commits to the block hash, so one comparison covers the whole chain below it. See [l1.md](l1.md). |
| 2026-10-04 | **Unichain (chain id 130) is supported as a second chain.** One node and one database per chain: `OP_INDEXER_CHAIN_ID` picks the chain, and every per-chain value (signer, bootnodes, fork times, block time, dispute game factory) comes from `op-indexer-chainspec`. Unichain has no legacy chain (it was born in Bedrock format, November 2024), makes a block every second, and has its own `DisputeGameFactory`, whose games are super games (type 9). Limits that are really times follow the chain's block time or are times: the unsafe store's retention follows its keys' 24-hour expiry, and gossip scoring's slot is the block time. Promotion walks a safe-head move down in 1,024-block reads (up to 16,384 blocks) instead of one read. | A second OP Stack chain checks that nothing assumes OP Mainnet. One database per chain keeps the stores and their limits simple. Redis keys carry the chain id, so two chains can share one Redis server. The data directory cannot be shared: the archive and the node store record their chain (id and genesis hash) when created, and a node of another chain refuses them. One made by an earlier build is recorded as OP Mainnet's if it holds data (earlier builds ran nothing else) and as the configured chain's if it is empty. At 1 s blocks an hourly game moves the safe head by 3,600 blocks, which one 1,024-block read would leave as a hole. Nothing on Unichain has run yet. |
| 2026-10-04 | **The retry policy lives in `storage`** (`op_indexer_storage::retry`); `pipeline` and the importer both use it. | The importer writes to the stores without the pipeline and needs the same backoff. |
| 2026-10-04 | **The node is a source of data, streamed out; ClickHouse leaves the project.** Committed blocks are kept in the local block archive (fjall), unsafe blocks in Redis, as before. Consumers subscribe over **gRPC with protobuf** (tonic, prost) and get history from the archive followed by the live chain, with each block's status (unsafe, safe, finalized) and reorg notices. Each subscription chooses **decoded records** (header fields, transactions with senders, receipts, logs) or the **raw consensus encoding** (header, body and receipts as stored). The committed heads and transaction senders move into the archive. The `query` crate is not built; the stream replaces it. | A data source serves many consumers better than one database: each pipeline keeps the copy it needs, and the node stays a single binary with Redis beside it. gRPC gives server streaming with backpressure and generated clients in every major language; Cap'n Proto's Rust RPC is less used. Offering raw bytes costs little and spares consumers that decode themselves. |
| 2026-10-04 | **Pre-Bedrock blocks are shared only among op-p2p-indexers; everything else syncs from and gives back to the normal network.** Our nodes advertise an op-p2p-indexer entry in their discovery record. Pre-Bedrock blocks are fetched from and served to only peers with that entry, over the eth protocol we already speak; post-Bedrock blocks are fetched from any execution peer and served to any, within limits that keep us a light, polite peer (few sessions, paced requests, no slot held idle). | No standard node serves the legacy chain, and standard nodes do not expect it; keeping it among indexers spreads it without loading the shared network. A flag in the record needs no new protocol. |
| 2026-10-04 | **The archive keeps the whole history, and the committed heads only rise.** The retention window (`OP_INDEXER_ARCHIVE_RETENTION_BLOCKS`), `ArchiveStore::trim` and `ArchiveStore::truncate_above` are removed; promotion ignores a safe head at or below the committed one instead of rolling the archive back. Promotion checks each block's transactions and receipts roots over the bytes it writes and refuses a block that does not match; serving checks the unsafe store's bodies and receipts the same way. Promotion, the commitment task, the range task, the L1 heads forwarder and the range sync planner stop the node if they end before shutdown. Range sync without the L1 side stays allowed: such an archive holds blocks not committed on L1 (unsafe in the stream), and an unsafe reorg deeper than 64 blocks needs a rebuild. | The archive is the history the node serves and streams, and an import fills it whole. Safe heads come from bonded dispute games the commitment task matched and never publishes below the committed one, so the rollback path was unreachable, and it was the only thing that deleted committed blocks. A task that stops silently leaves the archive behind while the node looks healthy. |
| 2026-10-04 | **Base (chain id 8453) is supported as a third chain, with its own forks from Azul, and the node stops at a fork it does not know.** Base left the OP Stack (2026-02) and the Superchain Registry (2026-04-27); its values come from its own repository, `base/base`. It is one chain from genesis: the OP rules through Jovian, then Base's forks Azul (2026-05-28), Beryl and Cobalt, each a time fork in the chain's fork list like any OP fork. A chain's time forks are a per-chain list (`ChainSpec::time_forks`), not fixed fields; a chain has the forks it lists. Base's execution nodes discover each other on a discv5 network of their own (protocol id `basev0`, own bootnodes), so the chain spec carries an execution discovery identity and separate consensus and execution bootnodes. Its L1 commitment is a new game type, `AggregateVerifier` (621), created with `createWithInitData`; game formats are a per-chain table by game type. Base's consensus nodes do not serve `payload_by_number`, so gaps fill through execution range sync only. When execution peers announce a fork this build does not know, or the sequencer signs a payload this build cannot decode, the node stops instead of storing blocks it cannot verify; EIP-8130 transactions (type `0x79`, Base's unscheduled Everest) are refused that way until they are supported. | Base still uses the OP formats for gossip, payloads, headers, receipts and output roots, and every Base fork so far changes only its EVM, RPC and L1 contracts, so a fork list and a few per-chain values model it; no protocol family is needed. Base plans about six forks a year, so a fork the build does not know must stop the node loudly rather than freeze it quietly. Investigation and sources: `docs/base.md`. |
| 2026-10-04 | **Four binaries, for one user and for serving at scale.** **`indexer`**: the full node for a single user, every service in one process with the fjall archive (what exists today). **`server`**: also a full node (p2p layers, its own unsafe chain, serving peers), but stateless for history: it keeps no chunk cache and reads sealed, immutable block chunks from R2 on demand, streaming them with a bounded in-memory read-ahead (R2 holds only sealed history, never live data; a global hash index in R2 answers lookups by hash). One server per deployment also exports newly sealed chunks. **`importer`**: the existing `import` tool, which produces the chunks. **`balancer`**: the single entry point for users and the job-distribution service: it keeps the servers' health and load and splits each request into per-chunk jobs spread over them (Flight `GetFlightInfo` endpoints per chunk, least loaded first; a locate call for gRPC subscriptions); no data flows through it. Chunks are sealed only when all their blocks are finalized and have receipts, so they never change. Spec: `docs/serving.md`; built after Base. Redis leaves the project: the unsafe chain lives in memory in the node, journaled to fjall. | Committed history never changes, so immutable range files in object storage, read directly by stateless servers, scale out by network rather than storage: cheaper, simpler and faster than one database or one cache per node, while every server still takes part in the p2p networks. R2 egress is free and its reads cost about $0.01 per TB streamed. Keeping the data out of the balancer keeps it small and never the bottleneck; Flight is built for per-chunk endpoints. The single-user `indexer` stays simple. |
| 2026-10-04 | **Settings come from a `.env` file; Docker is dropped for now.** Every binary loads `.env` from the current directory at startup (or `--env-file <path>`, or `OP_INDEXER_ENV_FILE`) with `dotenvy`, before anything reads the environment; a variable already set in the process wins. One `.env.example` lists every variable of every binary with its default; each binary reads only its own, so one `.env` serves them all. The Dockerfile, the compose file and its per-instance env files are removed: several instances on one host each get a data directory, ports and a `.env`. | One file per instance replaces the compose variables, and the binaries need no service, so a container adds little until deployment needs one. Values are never logged: the files hold the R2 keys, the API keys and the Envio token. |
| 2026-10-04 | **Importer feasibility, measured on 1,009 OP Mainnet blocks.** HyperSync has the whole range from block 0 with every header field; every rebuilt header hashed to its block hash, every transaction to its hash, every transactions and receipts root matched (legacy receipts in their plain encoding); L1-to-L2 messages have a zero signature and a zero-address sender. About 7 KB of JSON per block; a 1,000-block query took 1.3 s. The API token then allowed unlimited requests for 30 minutes from first use, so the download does nothing but download and resumes. | The basis of [import.md](import.md). |
| 2026-10-04 | **OP Mainnet imported whole.** On a 32-core server `download` fetched blocks 0 to 157,745,023 (589 GB) in about 25 minutes at 300 to 380 MB/s; that build's `verify` (writing a verified copy, no sender recovery) accepted all 630,336 downloaded chunks, its top block matching the newest dispute game (type 9); the fjall bulk load (since removed) ran at 190,000 to 235,000 blocks/s. Unichain: 604,009 chunks downloaded; `verify` stopped at block 16,068,511 on a missing authorization list, which led to the fill from the chain's RPC; then verified and exported to `unichain-snapshot` (1,693 chunks, 0 to 60,400,897); a catch-up chunk to 60,422,316 followed on 2026-10-05. | The first whole-chain runs; their checks of the fill (lists, holes, source hashes, header fields, each with a block fetched as a hole) ran offline against a local stub, not HyperSync. |
| 2026-10-04 | **Chunks: zstd level 1 in 1 MiB segments (D3), 256 MiB uncompressed, at most 100,000 blocks (D4).** On 2,000 post-Isthmus OP Mainnet blocks (146.9 MB of records), `zstd -b`, one thread: level 1 7.0× at 1.2 GB/s compress, 3.4 GB/s decompress (6.6× in 1 MiB segments); `--fast=1` 6.4×; level 3 8.3× at 0.9 GB/s, decompressing as fast; level 19 9.8× at 4 MB/s. Bigger chunks gained 1.5 % at level 3. | CPU weighs more than R2 storage; segments let one block be read without the whole chunk; 256 MiB makes a GET mostly transfer, not time to first byte, and a chunk one Flight job. |
| 2026-10-05 | **The importer's `verify` checks and uploads in one pass; `export` and the verified copy are removed.** Each downloaded chunk is rebuilt and checked (header hash, links, roots, every sender), sealed into the D4 chunks and uploaded; the downloaded chunks a recorded upload covers are deleted. The chunks are listed in the manifest, with the hash index, only once the last block matches the anchor; links are checked as chunks are sealed. `run` is `download` then `verify`. | Base is 2.57 TB of downloaded chunks on a disk with 0.99 TB free: a verified copy of every chunk could not fit. Uploading unlisted until the anchor holds keeps the trust rule (nothing is served before the range is proven) without a local copy; the objects of a failed range are unlisted and read by nobody. |
| 2026-10-05 | **Each HyperSync answer is checked for completeness and asked again; incomplete ranges are fetched again later.** An answer lacking rows or fields its blocks need is asked again (up to 8 answers, keeping the most complete, or after 3 in a row no better), fills are merged field by field, user deposits' `mint` is rebuilt from their L1 logs, and `download --refetch-incomplete` records the ranges still lacking (`refetch.json`) and fetches only those, scanning only each chunk's head unless `--scan full`. | On Base, HyperSync answered the same query completely only 4 times in 5, and some of its deposit rows lack `mint`; a block that does not hash cannot be sealed, and downloading 2.57 TB again was not an option. |
| 2026-10-05 | **Simplification branch ([#13](https://github.com/eabz/op-p2p-indexer/pull/13)).** Environment, tracing and signals move into `runtime`; keys, Flight tickets and Arrow schemas into `api`, so the balancer no longer depends on the node, the stream implementation or storage. R2 settings are parsed once. Opt-in `live`, `archive` and `fleet` profiles are checked at startup. Node wiring, sync coordination, persistence and supervision are split, every task is named and an unexpected exit stops the node. Each Flight and subscription history reader owns its archive stream and cancellation (the shared cursor map and idle eviction are removed). Dead code removed: `StorageError::is_archive_locked`, bounds `ArchiveStore` already gives; `Table::schema()` returns `SchemaRef`. Checked locally: all binaries build and pass the lint gates, profiles reject bad combinations, nodes start and stop cleanly, ranged reads over real fjall and a controlled chunk source, all 64 Arrow fields unchanged. | Smaller crates with one job each, and readers that cannot stall one another. Local checks do not replace the live runs recorded below. |
| 2026-10-05 | **`indexer`, `server` and `balancer` run in the background themselves**: `start`, `stop`, `restart`, `status`, `logs` and `install-service` (writes a systemd unit), plus `--version` on every binary. | Operators ran them by hand under `nohup`; no Docker setup exists. |
| 2026-10-05 | **Sealed reads read only what each answer needs, and check segments rather than headers.** A read asks for a block whole, without its blooms, or without its receipts (`ReadParts`); each Flight table, subscription format and peer answer asks for the least. Every segment's sha256 is checked against the chunk's index, whose own hash is in the manifest; the per-header keccak and parent-link checks remain only in `import fetch` and single-block reads. Flight builds are capped server-wide (2 per core). Measured: archive reads 4.1 s of CPU per GB whole, 1.85 s without blooms, 0.94 s without receipts; Flight CPU per Arrow GB, blocks 481 → 114 s, transactions 8.7 → 3.7, receipts 136 → 83, logs 6.8 → 4.5; one R2 stream 63 → 247 MB/s with 150 ms per GET. | A chunk proven at seal time is proven by its hashes; recomputing keccak per header doubled the CPU per byte. With 48 streams, unbounded builds exhausted memory and a hold-and-wait cap deadlocked, so a build is taken only when free, after flushing. |
| 2026-10-05 | **Servers serve execution peers from the chunks**, through the same sealed reads, keeping session slots for nodes that need their history. | A server holds no local history, and a node bootstrapping from peers needs someone who has it. |
| 2026-10-05 | **Raw chunks are downloaded straight from R2**: the balancer signs time-limited URLs and `import fetch` downloads and checks them. An optional Cloudflare cache can sit in front of the bucket. | Raw history needs no server CPU; R2 egress is free. |
| 2026-10-05 | **Unknown forks, as built.** The execution side only warns: once 3 distinct hosts announce the same unknown `next` fork time, it is the horizon and the operator is told to upgrade before it; nothing is refused. The node stops on gossip instead: 3 distinct sequencer-signed blocks it cannot read within 600 s mean the protocol changed under this build (`NetworkError::ProtocolChanged`). This replaces the stop on execution peers' announcements in the 2026-10-04 Base row. | A fork id in a node record or one peer's status can be forged; the sequencer's signature cannot, and it signs only valid blocks. |
| 2026-10-05 | **Run live.** Unichain from R2: three servers and a balancer serving 1,694 chunks. Range sync, including a deep hole. L1 commitment end to end: light client bootstrapped, games matched, safe and finalized heads raised. Flight on v0.1.8 from a non-local client: blocks 129.6 MB/s on 48 streams, transactions 406 MB/s, logs (lz4) 329 MB/s. Base: download done, refetch in progress. The exporter runs; sealing not yet seen. | The first evidence of the platform end to end; what remains is in [roadmap.md](roadmap.md). |
| 2026-10-05 | **`.env` holds only what differs between machines: what to run, secrets, and where things are** (63 variables in `.env.example` down to 23). The tuning knobs are sized from the machine's cores and memory (Linux `/proc/meminfo` and the cgroup limit, macOS `hw.memsize`) and logged at startup: the unsafe chain's cap, the Flight builds (now `OP_INDEXER_STREAM_MAX_BUILDS`) and streams, the server's execution sessions and read budget (`crates/node/src/sizing.rs`). The importer's options are flags; only the token, the state directory, the endpoints, the chain and R2 fall back to the environment. Derived: `OP_INDEXER_SERVER_ID` from the host name, the exporter's name from it, `OP_INDEXER_SERVER_ADDRESS` from the stream's listen address or, on every interface, the public IP execution discovery learns, and the switches L1 → range sync → execution network. Every other variable is still read and documented in [configuration.md](configuration.md), "Advanced settings"; removed ones are read for one more release with a warning naming the replacement. | A setting that depends on the machine was wrong as a fixed default: 8 Flight streams and 2 GiB of unsafe chain on a 64-core server or a 4 GiB VM alike. A setting nobody changes is noise in the one file each operator edits. Flags suit the importer, which runs by hand and records its range in its plan; endpoints stay in the environment because their URLs carry keys, which a flag shows in `ps`. |
