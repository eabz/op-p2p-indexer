# L1 spec (`crates/l1`)

Status: **built**, off by default (`OP_INDEXER_L1_ENABLED`). The beacon light client has run
live and follows mainnet (§8); the execution-p2p half (§6) and the pipeline's side have not
run from crate code, and the chain has never run end to end. The light client saves its newest
finalized beacon block and a restart bootstraps from it (§8, "Restart"; run 2026-10-05 with
the light client alone, not yet inside a full node). The viability test is [l1-viability.md](l1-viability.md).

The `l1` crate tells the indexer which L2 blocks are committed to L1: the **safe** and
**finalized** heads. There is no provisional safe head (a fixed lag behind the gossip head):
it would give no guarantee. Like everything else in the indexer it uses no RPC: it follows
Ethereum over its own p2p networks and verifies what it is told.

## 1. What "committed to L1" can mean

| | What it is | What it needs | Granularity |
|---|---|---|---|
| **A. Derived safe head** | The L2 blocks whose batches are on L1, exactly as an op-node derives them | L1 headers, batcher transactions, **blob data**, batch decoding, deposit logs | Every L1 block (seconds to minutes behind the tip) |
| **B. Proposed head** | The L2 block of the newest dispute game created on L1, whose claim commits to that block's output root | L1 headers, the receipts and one transaction of the L1 blocks that create a game | About hourly |

B is what the importer already uses as its top anchor (`docs/import.md` §11), there read
through HyperSync; here it is read from L1 peers and verified.

**B is built first, A later.** B needs no blob data, no batch decoding and no KZG
cryptography; it gives a head that L1 really carries a claim for, checked against our own
block's output root. Its cost is freshness: about an hour behind the tip. A is the
complete answer and a much larger project: since the PeerDAS upgrade blobs travel as data
columns, which have to be fetched from beacon peers, verified with KZG proofs and reassembled
before a batch can be read.

## 2. Parts, for B

1. **L1 header trust: a beacon light client.** Ethereum's light client protocol over libp2p
   (bootstrap from a trusted checkpoint, then sync-committee updates, finality updates and
   optimistic updates) gives verified beacon headers, each carrying its execution block hash
   and number. Signatures are BLS aggregates of the sync committee.
2. **L1 block data: execution p2p.** The `el` crate's session code speaks the same protocol
   L1 execution nodes do (different network id, genesis and fork id). For an L1 block hash the
   light client vouches for: its header (must hash to that hash), and, when the header's logs
   bloom may contain the dispute game factory's event, its body (against the transactions
   root) and, when a transaction in it was sent to the factory, its receipts (against the
   receipts root).
3. **The watcher.** Finds `DisputeGameCreated` events of the chain's factory and reads the L2
   block and output root from each game (`op-indexer-chainspec`'s `game.rs` decodes both
   claim formats, for this crate and the importer). It publishes the recent games on the L1
   chain it walked, and the highest finalized L1 block on that chain.
4. **Output.** `watch<L1Games>` into the pipeline, whose commit task checks the games against
   our own blocks and publishes the `L1Heads` that promotion follows: **safe** = the highest
   L2 block a recent game's claim matches; **finalized** = the same, among games whose L1
   block is finalized.

A disagreement between a game's claim and our block is not ignored: it is logged loudly, and
that game moves no head. A higher game that matches still does.

## 3. Trust

- The light client needs one trusted value: a recent finalized beacon block root (a weak
  subjectivity checkpoint), given in configuration. Everything after it is verified. The
  finalized block it saves for restarts adds no trust: it was verified from that checkpoint.
- Nothing from an L1 execution peer is trusted: headers by hash, receipts and transactions by
  the roots in a verified header.
- A dispute game is a bonded claim, not a proof. **"Safe" here means "a bonded claim on L1
  equals our block", not "the batch is on L1".** The game's type is not checked against the
  respected game type of the chain's portal, and anyone who posts the bond can create a game:
  a game of any type from anyone counts, and a game can still be challenged. A false claim
  cannot match our block, so it moves nothing; a true one from anyone does. "Finalized"
  means the claim's L1 block is finalized, not that the game has resolved. Both are stated
  wherever the heads are shown. Checking the respected type is not built.

## 4. The viability test's answers

Measured 2026-10-04; details, numbers and sources in [l1-viability.md](l1-viability.md).

- **Beacon light client**: recent Lighthouse (v8.2) serves bootstrap, finality, optimistic
  updates and updates by range to an unknown peer; older Lighthouse lists the protocols and
  answers empty, Prysm does not list them, other clients were not reached over TCP. A cold
  start verifies its first finalized block and head in under 20 s.
- **Crates**: nothing published covers the light client; it is built on sigp's SSZ and
  tree-hash crates and `blst` (+7 lockfile packages, `cargo deny` clean).
- **L1 execution peers**: the `el` session code works unchanged (network id 1, eth/69, fork
  id from `alloy-hardforks`), and a serving peer answers in about 0.15 s for blocks up to 30
  days back. But slots are scarce: one serving session per 4.5 to 15.5 minutes of dialing,
  both times Geth.
- **Bloom filter**: weak on mainnet (one header in five passes address and topic); the
  watcher reads bodies first.
- **Checkpoint**: an operator supplies a recent finalized root from a source they trust, for
  the first start (later starts use the saved one, §8); how old a checkpoint peers still serve
  was not measured.
- **End to end**: a known game was found and decoded from L1 peers with only the light
  client's hash trusted, by the probe; not yet from crate code.

## 5. Not built

Derivation from batches (A), blob and data-column handling, deposits from L1 logs, reorg
handling of the safe head beyond "the head does not move back unless L1 finality says so"
(to be specified with the unsafe store's reconciliation, `docs/storage.md` §3.2).

## 6. The execution-p2p half (`crates/l1`): not run from crate code

Interfaces between the three parts:

- **In** (from the beacon light client, §8): `mpsc::Receiver<TrustedL1Block>`,
  `TrustedL1Block { number, hash, finalized }`. A head as attested (`finalized: false`) or a
  finalized block (`true`); not necessarily consecutive, in any order. Nothing else is taken
  on trust.
- **Out** (to the pipeline's consumer, `crates/pipeline/src/commit.rs`):
  `watch::Receiver<L1Games>`, `L1Games { recent, finalized_l1_block }` of `VerifiedGame {
  l1_block, game, game_type, l2_block, output_root, timestamp }` (in primitives). `recent` is
  the 64 most recent games on the L1 chain linked by parent hashes down from the newest
  block walked, oldest first: all of them, not only the newest, since the newest may claim a
  block that is not ours. A game below a break in that chain (a block not walked yet, or one
  of another chain) is held back until the break is walked, and dropped with its block if
  that comes first. `finalized_l1_block` is the highest finalized L1 block whose hash is on
  the linked chain, so every published game at or below it is on the finalized chain.
  The commit task (`crates/pipeline/src/commit.rs`) checks the games against our own blocks
  with `VerifiedGame::check`, highest L2 block first: the output root from our header, the
  timestamp for super games, and the block must be from Isthmus on (before it, the header's
  withdrawals root is the empty-trie root, not the message passer's storage root, so the
  claim cannot be checked). The highest match is the safe head, the highest match in a
  finalized L1 block the finalized head. It judges again every 12 s, so a game that did not
  match is judged again once our block at that height changes. A game that matched is
  remembered while it is recent (the whole game, not its address, and our block's hash) and not read again, so
  it raises the finalized head when its L1 block finalizes even after promotion pruned the
  block from the unsafe store. The memory starts empty: after a restart, a finalized game at
  or below the committed safe head is judged from the archive, and with the block not in it
  it does not raise the finalized head. It never lowers a head, not across restarts
  either: it starts from the heads the archive recorded
  (`docs/pipeline.md`).
- **Junk games.** The bound of 64 is a liveness lever: 64 games created within the finality
  lag (64 bonds) push an honest game out before its L1 block finalizes, and the finalized
  head waits for the next honest game. Heads never go down. Likewise the first walk after a
  start ends at the first game 128 blocks below its start even if that game is junk; the
  honest games below it are then not seen. Keeping matched games from eviction would need a
  channel back from the commit task to the watcher, so it is not built.

How a trusted hash becomes a game:

1. `watch.rs` walks the headers down from the trusted hash (`GetBlockHeaders` by hash,
   falling): each header must hash to the hash named by its child, so the whole walk hangs on
   the trusted hash. It stops at a block it already knows. A block is recorded as walked only
   once it has been scanned (steps 2 to 4).
2. Each new header's logs bloom is tested for the factory's address and the
   `DisputeGameCreated` topic. A bloom has no false negatives, but on mainnet it is a weak
   filter: blooms are about three quarters full, and about one header in five passes (19%
   over 718 headers, measured 2026-10-04; 46% contain the address alone).
3. For a block whose bloom may match, `fetch.rs` reads the body (the transactions must hash
   to the header's transactions root). Only if one of its transactions was sent to the
   factory are the receipts read (counted against the transactions before decoding, blooms
   rebuilt, hashed to the header's receipts root: Ethereum receipts,
   `alloy_consensus::EthereumReceipt`). So about fifty bodies an hour, and receipts only for
   the blocks that create a game.
4. The factory's event gives the game, its type and its root claim; the transaction at the
   same index must be a call of the factory itself, and its calldata is decoded by
   `ChainSpec::game_claim` (chainspec, shared with the importer): the L2 block and output root
   of a fault game, or our chain's entry of a super game's super root.

- **Reorgs.** A trusted head that does not build on the blocks walked replaces them, with
  their games; so does a finalized block the walked chain does not hold. A finalized block
  counts only once its hash is on the linked chain. Finalized blocks are not replaced.
- **Start.** Nothing is stored between runs. The first trusted block is the light client's
  checkpoint, a finalized block, followed by heads within seconds. The first walk goes down
  until a game at least 128 blocks below its start has been found (old enough to be
  finalized), at most 7,200 blocks (a day).
- **Stops.** A walk that stops part-way (no peer served a block, or shutdown) after it
  recorded a block keeps where it stopped, and continues when the next trusted block
  arrives; a continued walk that stops again is kept, from where it stopped. It is closed
  once the block below the hole is the parent its child names (a hash, not just any block
  at that height: the one there may be of the chain a reorg replaced), or its child is gone.
  That includes the first walk. Games are published when a walk ends or stops, never in
  the middle: until a walk connects, the blocks below it count as unlinked, and the list
  would shrink for a moment to the games above.
- **Hand-off.** Trusted blocks that arrive during a walk wait in the channel; only the
  last head told (the light client's newest view, even if a reorg lowered it) and the newest
  finalized block of what waited are followed, the head first.
  The light client never waits on the watcher: it keeps the newest block of each kind it
  could not hand over and sends it later, so a long walk neither stalls it nor loses the
  newest block.
- **Faults.** A peer is blamed only for an answer that is wrong. A header that hashes to the
  trusted hash and does not decode, or a verification task that fails, is this node's
  failure: logged, the peer kept, another asked.
- **Peers.** `el`'s discovery, sessions and peer set are reused for a second network through
  `el::NetworkSpec` / `el::PeerNetwork` (network id 1, mainnet's genesis hash, the fork
  schedule from `alloy-hardforks`' `EthereumHardfork::mainnet()`, node record key `eth`), with
  its own node key and port. The node serves nothing on L1 and advertises the newest trusted
  block as its head. A peer whose answer fails verification is banned; one that does not
  answer is dropped; another peer is asked. The tuning for OP's few peers (fast discovery
  phase, quick redial of full peers) is left as it is: it does no harm with many peers.
- **Sessions are the hard part** (viability probe, 2026-10-04, a dial-only node behind NAT):
  the handshake works on eth/69 with every client and our fork id is accepted, but almost
  every peer is full: 804 dials to 400 peers over 19 minutes gave 692 "too many peers" and one
  serving session (a Geth node), after 15.5 minutes; a later run got one after 4.5 minutes,
  also Geth. Once in, headers, bodies and receipts each took about 0.1 to 0.15 s, for blocks
  up to 30 days back, all roots matching. So: candidates are dialed
  fewest-attempts first, up to one dial a second; a session is kept as long as it lives (a
  timeout or a block not held costs the peer nothing; only data that fails verification bans
  it); a peer that served is saved in the node store (`NodeStore::save_l1_peer`) and dialed
  first on the next start (`NodeStore::l1_peers`). An inbound port helps most:
  `OP_INDEXER_L1_ADVERTISED_ADDR` (§9).
- This half has not run from crate code: the numbers above are the probe's.

## 7. The beacon network (`crates/l1/src/beacon/network`)

The swarm side of the light client: it finds beacon peers, sends them the light client's
requests and hands over what they gossip. It decodes no light-client container and verifies
nothing; `client` and `verify` do. A small libp2p swarm of its own, not shared with `p2p`
(the two crates must not depend on each other, and they have nothing but the transport in
common).

- **To the light client** (`network/handle.rs`): `NetworkHandle::request(Request)` for a
  bootstrap, updates by range, the finality update or the optimistic update, answered with
  the successful chunks and the fork digest of each; `report_invalid(peer)` for data that
  failed verification; a bounded stream of `Gossip` messages, each answered with
  `report_gossip(id, peer, Verdict)`.
- **Swarm** (`network/behaviour.rs`): TCP, noise, yamux; identify; connection limits;
  gossipsub (StrictNoSign, snappy, the Altair message id) on
  `light_client_finality_update` and `light_client_optimistic_update` of the current fork
  digest; one request/response behaviour per protocol, with the consensus-specs framing of
  `rpc.rs` (varint length, snappy frames, result byte, fork digest).
- **Being a peer.** `Status`, `Ping` and `GetMetaData` (v2, v3) are answered and `Goodbye` is
  read. The status follows the light client's store. The metadata says no subnets and a
  custody group count of 4, the Fulu minimum: with 0, Lighthouse closed the connection 0.2 s
  after the answer (measured). The node keeps no data columns and serves none.
- **Peers.** Discovery passes on nodes whose record carries our fork digest. A peer is used
  if identify lists the light-client bootstrap protocol; its status must name our digest. A
  request goes to the peer that failed least and was asked longest ago. A bootstrap is not
  asked twice of a peer that answered it without data. Three answers in a row without data,
  a malformed answer, or a report from the light client drop a peer for good.
- **Connections are short.** Mainnet Lighthouse nodes are full and prune a peer without
  subnets at their next heartbeat: Goodbye 129 (too many peers) after 2 to 35 s. So a request
  without a peer waits (up to the request timeout) and leaves the moment a peer identifies,
  together with our status; a request whose connection closes under it goes to another
  peer; six peers are kept if they can be. A peer that was usable and hung up is remembered
  (64 of them) and dialed again after two minutes, then four, doubling up to five dials,
  because discovery reports a node once. A closed connection is never held against a peer;
  only a status that times out or names another digest is.
- **Gossip.** A message is held back until the light client's verdict: accepted (verified
  and newer than what is held) and it is forwarded to the mesh; rejected (does not verify)
  and the peer is dropped; ignored otherwise. Peers' subscriptions to other topics are not
  tracked.
- **Bounds.** 24 connections, 12 peers, 512 candidates, 64 known peers, 4,096 avoided peers; a
  response chunk is at most 64 KiB and a response at most 8 chunks, checked before
  decompression; every request ends within 20 s (10 s to find a peer, 10 s for its answer); a gossip frame is at most 1 MiB.
- **Fork digest.** Computed once at start from the beacon fork schedule in `spec.rs`, for
  discovery, our status and the gossip topics. After a beacon fork (or a blob-parameter
  change) the node has to be restarted, with a build that knows the fork. The light client
  itself accepts data under any digest whose containers it reads.
- **Run live** (2026-10-04, mainnet, a dial-only node behind NAT): bootstrap 17 to 21 s after
  start, then a verified head about every slot (39 trusted blocks in 7 minutes, 4 of them
  finalized, largest gap 19 s). With gossip verdicts in place, 200 s gave 18 trusted blocks
  from 31 gossip messages and 3 requests. The 32-minute run is in §8. Not yet run: a
  sync-committee period boundary, a fork.

## 8. The light client (`crates/l1/src/beacon/{client,verify,spec,types}.rs`)

- **Component**: `LightClient::new(BeaconConfig { checkpoint, saved, listen_addr, bootnodes },
  trusted: mpsc::Sender<TrustedL1Block>, finalized: watch::Sender<Option<BeaconCheckpoint>>)`,
  `run(cancel)`. The binary runs it when `OP_INDEXER_L1_ENABLED` is set, with
  `OP_INDEXER_L1_CHECKPOINT` and `OP_INDEXER_L1_BEACON_LISTEN_ADDR`, and saves what it
  publishes on `finalized` in the node store (below).
- **Restart.** Each newer finalized beacon block the light client verifies (about once an
  epoch, and the bootstrap's own) is published as a `BeaconCheckpoint`: its root and slot,
  and the configured checkpoint it was verified from. The node saves the newest in its node
  store (`NodeStore::save_l1_checkpoint`, in `node/`), which belongs to one chain and so to
  its L1, Ethereum mainnet. On start:
  - the saved block was verified from the configured checkpoint, so it is newer: the light
    client bootstraps from it, with the configured checkpoint as the fallback;
  - it was verified from another checkpoint: the operator configured a new one since, which
    is used first, with the saved one as the fallback (the configured checkpoint's slot is
    not known before its bootstrap, so the order follows the operator's change);
  - nothing is saved (first start), or it is the configured checkpoint itself: the
    configured one alone.

  When 12 peers refuse the first root's bootstrap, the fallback is tried; when it is refused
  too, the run ends with `CheckpointUnavailable` naming the configured checkpoint. Which root
  was used is logged with its slot. Nothing new is trusted: a saved block was verified, step
  by step, from a checkpoint the operator configured.
- **Restart, run** (2026-10-05, mainnet, the light client and the node store alone):
  - a first start bootstrapped from the configured root in 16 s and saved it, then saved the
    next finalized block 5.3 minutes later (slot +32);
  - a restart bootstrapped from that saved block in 33 s, the configured root as fallback;
  - a saved root no peer holds was given up after 12 refusals (73 s) for the configured root,
    and replaced by the next finalized block saved.

  Not run: both roots refused. Seen in the same runs: from a checkpoint a period behind the
  clock, the catch-up (`LightClientUpdatesByRange`) got no answer for 8 minutes (peers
  refused the protocol or timed out), so the light client stayed at its checkpoint: a
  checkpoint, saved or configured, from the current period is what works today.
- **Out**: the checkpoint's own execution block (finalized), then every newer finalized
  block and every newer attested head, each verified.
- **Verification** (`verify.rs`): the bootstrap against the checkpoint root; every update by
  slot order, the committee of its period, the execution-payload, finality and
  next-committee branches, and the committee's aggregate BLS signature; two thirds of the
  committee for both the finalized block and the head; rotation when the finalized header
  enters the next period. A committee's keys are decompressed and checked once. Data from a
  peer that fails verification gets the peer dropped; data that is only stale, ahead of our
  committees or clock, or weakly signed is ignored. Only the containers of Electra and later
  are read: the light client starts from a recent checkpoint.
- **What it asks** (`client.rs`): the bootstrap; `LightClientUpdatesByRange` when the next
  committee is unknown (every 10 minutes) or the clock has passed the last known period
  (every 20 s); otherwise nothing while gossip brings news, and the optimistic update every
  slot plus the finality update every epoch when it does not.
- **Updates by range** (`apply_light_client_update`): entries refused as stale are skipped,
  and the rest of the answer is still applied; an update that rotates the committees also
  adopts the next committee it carries, so the catch-up advances one period per update, not
  per request. An update with an empty finality branch carries no finality and is not held
  against the peer; as the specification has it (`process_light_client_update`), a next
  committee is learned only from an update with finality.
- **A checkpoint too old** for peers to serve its bootstrap, and its fallback too, ends the run
  with `CheckpointUnavailable` after 12 peers refused each with `ResourceUnavailable`
  (response code 3): the operator has to configure a newer one. Other codes, empty answers and closed
  connections do not count.
- **Head stall.** When the verified head has not moved for five minutes, a warning is
  logged, again every five minutes while it lasts: no peer serves updates, finality has
  stalled for more than a period, or the build is behind a fork. Measured from when the head
  last moved, so the bootstrap's old checkpoint slot does not set it off.
- **Run live** (2026-10-04, 32 minutes, mainnet, dial-only behind NAT): first finalized block
  at 18.9 s, first head at 20.1 s; then 155 heads covering 156 consecutive L1 blocks, median
  12 s apart, max 36 s; 6 finalized blocks; 4 requests; nothing failed verification. Not run:
  a period boundary, the multi-period catch-up, a too-old checkpoint, clients other than
  Lighthouse.
- **Known limits:**
  1. The fork digest is fixed at start (§7); after a fork the head-stall warning fires and
     the node needs a restart with a build that knows the fork.
  2. Inbound beacon peers count towards the dial target, which has no separate inbound cap,
     so they can fill it.
  3. The specification's forced update is absent: with finality stalled for more than a
     period the node stops advancing. That is safe, by design: it reports nothing it cannot
     prove final.

## 9. Configuration

Read by the binary (`bin/indexer/src/config.rs`):

| Variable | Default | What |
|---|---|---|
| `OP_INDEXER_L1_ENABLED` | `false` | Follow L1: run the light client and the L1 execution network, and promote on verified games. Without it there is no safe or finalized head and nothing is promoted. Needs `OP_INDEXER_EL_SYNC=true` (and so the execution network): promotion records only what the archive holds, and range sync fills the gaps gossip leaves. |
| `OP_INDEXER_L1_CHECKPOINT` | none, required when enabled | Root of a recent finalized beacon block, from a source the operator trusts: the one value taken on trust. Used on the first start, or when it is newer than the saved one (§8, "Restart"). |
| `OP_INDEXER_L1_LISTEN_ADDR` | `0.0.0.0:30304` | L1 execution p2p, TCP and UDP; must differ from `OP_INDEXER_EL_LISTEN_ADDR`. |
| `OP_INDEXER_L1_BEACON_LISTEN_ADDR` | `0.0.0.0:9001` | The light client, TCP and UDP; next to the usual beacon port, 9000. |
| `OP_INDEXER_L1_ADVERTISED_ADDR` | unset | Public `ip:port` (same for TCP and UDP) in the L1 node record; unset, the address other peers observe. Worth setting on a server with a public address: L1 peers have few free slots, and a node they can dial gets sessions it would not get by dialing. |
