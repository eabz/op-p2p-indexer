# L1 spec (`crates/l1`)

Status: **being built** (user, 2026-10-04: no provisional safe head; a real L1 commitment as
fast as possible). The execution-p2p half and the pipeline's side are being written while the
viability test of the beacon light client runs; the light client is the critical path.

The `l1` crate tells the indexer which L2 blocks are committed to L1: the **safe** and
**finalized** heads. A provisional safe head (a fixed lag behind the gossip head) was built and dropped: it gave
no guarantee. Like everything else in the indexer it uses no RPC: it follows
Ethereum over its own p2p networks and verifies what it is told.

## 1. What "committed to L1" can mean

| | What it is | What it needs | Granularity |
|---|---|---|---|
| **A. Derived safe head** | The L2 blocks whose batches are on L1, exactly as an op-node derives them | L1 headers, batcher transactions, **blob data**, batch decoding, deposit logs | Every L1 block (seconds to minutes behind the tip) |
| **B. Proposed head** | The L2 block of the newest dispute game created on L1, whose claim commits to that block's output root | L1 headers, the receipts and one transaction of the L1 blocks that create a game | About hourly |

B is what the importer already uses as its top anchor (`docs/import.md` §11), there read
through HyperSync; here it would be read from L1 peers and verified.

**B is built first, A later.** B needs no blob data, no batch decoding and no KZG
cryptography; it gives a head that L1 really carries a claim for, checked against our own
block's output root. Its cost is freshness: about an hour behind the tip. A is the
complete answer and a much larger project: since the PeerDAS upgrade blobs travel as data
columns, which have to be fetched from beacon peers, verified with KZG proofs and reassembled
before a batch can be read.

## 2. Parts, for B

1. **L1 header trust: a beacon light client.** Ethereum's light client protocol over libp2p
   (bootstrap from a trusted checkpoint, then sync-committee updates, finality updates and
   optimistic updates) gives verified beacon headers, each carrying its execution block hash
   and number. Signatures are BLS aggregates of the sync committee.
2. **L1 block data: execution p2p.** The `el` crate's session code speaks the same protocol
   L1 execution nodes do (different network id, genesis and fork id). For an L1 block hash the
   light client vouches for: its header (must hash to that hash), and, when the header's logs
   bloom may contain the dispute game factory's event, its receipts (against the receipts
   root) and the creating transaction (against the transactions root).
3. **The watcher.** Finds `DisputeGameCreated` events of the chain's factory, reads the L2
   block and output root from the game (the importer's `game` module has the decoding for both
   claim formats), checks the claim against the output root of our own block at that height,
   and publishes the heads: **safe** = the newest game whose L1 block the light client has
   seen; **finalized** = the newest game whose L1 block is finalized.
4. **Output.** `watch<L1Heads>` into the pipeline, which already promotes on it.

A disagreement between a game's claim and our block is not ignored: it is logged loudly and
the head does not advance past it.

## 3. Trust

- The light client needs one trusted value: a recent finalized beacon block root (a weak
  subjectivity checkpoint), given in configuration. Everything after it is verified.
- Nothing from an L1 execution peer is trusted: headers by hash, receipts and transactions by
  the roots in a verified header.
- A dispute game is a bonded claim, not a proof. "Safe" here means "claimed on L1 and equal to
  what we hold"; a game can still be challenged. "Finalized" means the claim's L1 block is
  finalized, not that the game has resolved. Both are stated wherever the heads are shown.

## 4. Open questions for the viability test

- Do beacon nodes reachable over libp2p serve the light client protocol to an unknown peer
  (which clients, how many, how reliably), and what does bootstrapping from a checkpoint cost?
- Which maintained crates cover the light client (types, sync-committee verification, BLS),
  and what do they add to the dependency tree and to `cargo deny`?
- Can the `el` session code talk to L1 mainnet execution peers unchanged (network id, fork
  id, eth version), and do they serve headers, bodies and receipts for recent blocks to a
  node that only asks? L1 has thousands of nodes, unlike OP Mainnet's few dozen.
- How often does the factory's event appear, and is the bloom filter selective enough that
  receipts are fetched for few blocks?
- Where does the checkpoint come from in practice, and how old may it be?

## 5. Not in the first version

Derivation from batches (A), blob and data-column handling, deposits from L1 logs, reorg
handling of the safe head beyond "the head does not move back unless L1 finality says so"
(to be specified with the unsafe store's reconciliation, `docs/storage.md` §3.2).

## 6. What is built: the execution-p2p half (`crates/l1`), not yet run

Interfaces, agreed between the three parts:

- **In** (from the beacon light client, Worker 3's half): `mpsc::Receiver<TrustedL1Block>`,
  `TrustedL1Block { number, hash, finalized }`. A head as attested (`finalized: false`) or a
  finalized block (`true`); not necessarily consecutive, in any order. Nothing else is taken
  on trust.
- **Out** (to the pipeline's consumer, `crates/pipeline/src/commit.rs`):
  `watch::Receiver<L1Games>`, `L1Games { newest, finalized }` of `VerifiedGame { l1_block,
  game, game_type, l2_block, output_root, timestamp }` (in primitives). `newest` is the newest
  game on the L1 chain walked from the trusted head; `finalized` the newest in a finalized L1
  block. The consumer checks each against our own block with `VerifiedGame::check` (output
  root from our header, and the timestamp for super games) and turns a match into the safe or
  finalized head; it never lowers a head.

How a trusted hash becomes a game:

1. `watch.rs` walks the headers down from the trusted hash (`GetBlockHeaders` by hash,
   falling): each header must hash to the hash named by its child, so the whole walk hangs on
   the trusted hash. It stops at a block it already knows.
2. Each new header's logs bloom is tested for the factory's address and the
   `DisputeGameCreated` topic. A bloom has no false negatives; most blocks end here.
3. For a block whose bloom may match, `fetch.rs` reads the body (the transactions must hash
   to the header's transactions root) and the receipts (counted against the transactions
   before decoding, blooms rebuilt, hashed to the header's receipts root: Ethereum receipts,
   `alloy_consensus::EthereumReceipt`).
4. The factory's event gives the game, its type and its root claim; the transaction at the
   same index must be a call of the factory itself, and its calldata is decoded by
   `ChainSpec::game_claim` (chainspec, shared with the importer): the L2 block and output root
   of a fault game, or our chain's entry of a super game's super root.

- **Reorgs.** A trusted head that does not build on the blocks walked replaces them, with
  their games; `newest` can then be an older game. Finalized blocks are not replaced.
- **Start.** Nothing is stored between runs: the first trusted head is walked down until a
  game at least 128 blocks below it has been found (old enough to be finalized), at most
  7,200 blocks (a day).
- **Peers.** `el`'s discovery, sessions and peer set are reused for a second network through
  `el::NetworkSpec` / `el::PeerNetwork` (network id 1, mainnet's genesis hash, the fork
  schedule from `alloy-hardforks`' `EthereumHardfork::mainnet()`, node record key `eth`), with
  its own node key and port. The node serves nothing on L1 and advertises the newest trusted
  block as its head. A peer whose answer fails verification is banned; one that does not
  answer is dropped; another peer is asked. The tuning for OP's few peers (fast discovery
  phase, quick redial of full peers) is left as it is: it does no harm with many peers.
- **Not confirmed live**: that our session code completes a handshake with L1 mainnet peers
  and that they answer headers, bodies and receipts for recent blocks to a node that only
  asks (the viability probe's first step). The `el` metrics are not labelled by network yet,
  so L1 and L2 sessions are counted together.
